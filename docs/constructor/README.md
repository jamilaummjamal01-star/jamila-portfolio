# Закрытый конструктор общения с клиентами

## Цель

Создать внутри существующего сайта отдельный приватный рабочий кабинет, который заменит ежедневный поиск по длинным страницам Notion.

Конструктор должен помогать пройти путь:

`клиент → контекст → вопросы → ответы → диагностика → решение → стоимость → КП → следующий контакт`.

Notion остаётся архивом и источником импорта. Основная рабочая база конструктора хранится в Cloudflare D1.

## Текущий технический контекст

- приложение: React 19 + Next 16;
- сборка: Vinext + Vite;
- размещение: Cloudflare Worker;
- база: Cloudflare D1 через binding `DB`;
- ORM уже установлен: Drizzle ORM;
- публичный сайт не должен содержать ссылку на кабинет;
- доступ к кабинету защищается Cloudflare Access на отдельном поддомене или пути.

## Рекомендуемый адрес

`constructor.shakurova-content.ru`

Отдельный поддомен предпочтительнее пути `/constructor`, потому что:

- защита Cloudflare Access применяется ко всему приложению;
- API нельзя случайно открыть вместе с публичным сайтом;
- публичная навигация и SEO полностью отделены;
- можно независимо менять интерфейс кабинета.

## Архитектура

```text
Cloudflare Access
       │
       ▼
Private constructor UI
       │
       ├── Server actions / API routes
       │       ├── проверка Access identity
       │       ├── фильтрация базы
       │       ├── сохранение сессий
       │       ├── расчёт стоимости
       │       └── сборка черновика КП
       │
       └── Cloudflare D1
               ├── справочники
               ├── атомарная база знаний
               ├── клиенты
               ├── диагностические сессии
               ├── тарифы и расчёты
               ├── коммерческие предложения
               └── журнал изменений
```

## Главные продуктовые режимы

1. **Подготовиться к клиенту** — аудит, вопросы, риски и сценарий первого контакта.
2. **Клиент задал вопрос** — быстрый поиск готового ответа с вариантами тона.
3. **Провести диагностику** — пошаговая сессия с сохранением ответов.
4. **Собрать предложение** — диагноз, пакет, расчёт и черновик КП.
5. **База знаний** — редактирование и пополнение всех атомарных записей.
6. **Клиенты** — CRM-карточки, история и следующие действия.

## Основные решения

### 1. Не переносить страницы Notion целиком

Каждый смысл хранится как отдельная запись. Например:

- один вопрос клиенту;
- один вопрос клиента;
- один ответ;
- одно возражение;
- один красный флаг;
- один блок КП.

### 2. Одна запись может принадлежать нескольким контекстам

Например, вопрос о точности упаковки относится одновременно к:

- косметике;
- упакованным продуктам;
- БАДам;
- маркетплейсам;
- этапам диагностики и согласования.

Поэтому связи «запись ↔ ниша», «запись ↔ этап» и «запись ↔ подниша» должны быть many-to-many.

### 3. Ответы не генерируются без опоры на базу

Первая версия использует только сохранённые и проверенные записи. AI-адаптация тона добавляется позже и получает выбранные записи как источник.

### 4. Внутренние и клиентские данные разделены

Клиент не видит:

- коэффициенты ценообразования;
- внутреннюю себестоимость;
- красные флаги;
- служебные заметки;
- внутренний рейтинг клиента.

### 5. Любую запись можно обновить без релиза сайта

Редактор базы знаний работает прямо в закрытом кабинете. Контент хранится в D1, а не жёстко в компонентах React.

## Границы MVP

В первую рабочую версию входят:

- закрытый доступ;
- справочники 22 ниш и этапов сделки;
- атомарная база знаний;
- поиск и фильтры;
- режимы «что спросить» и «что ответить»;
- диагностическая сессия;
- клиенты и история;
- избранное;
- калькулятор стоимости;
- черновик КП;
- импорт JSON/CSV из подготовленной выгрузки Notion;
- экспорт резервной копии.

Не входят в первый релиз:

- автоматическая публикация контента;
- доступ для клиентов;
- несколько ролей пользователей;
- AI без проверки источников;
- синхронизация Notion в реальном времени;
- автоматическая отправка сообщений.

## Порядок реализации

1. Утвердить модель данных и карту экранов.
2. Добавить D1 binding и миграции.
3. Создать закрытый layout кабинета.
4. Реализовать базу знаний и фильтры.
5. Импортировать общее ядро и одну пилотную нишу.
6. Реализовать диагностическую сессию.
7. Подключить клиентов, стоимость и КП.
8. Защитить поддомен через Cloudflare Access.
9. Протестировать на реальных клиентах.
10. Последовательно наполнить все 22 ниши.

## Критерий готовности первого этапа

Первый этап завершён, когда в репозитории есть:

- согласованная схема данных;
- карта экранов;
- классификация контента;
- первая D1-миграция;
- план импорта текущей базы Notion;
- список решений, которые не требуют повторного обсуждения при разработке UI.
