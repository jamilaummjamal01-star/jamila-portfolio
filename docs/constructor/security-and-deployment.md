# Безопасность и размещение закрытого конструктора

## Требование

Конструктор, его API и данные должны быть доступны только Джамиле. Отсутствие ссылки в публичном меню не является защитой.

## Рекомендуемая модель

### Отдельный hostname

`constructor.shakurova-content.ru`

Публичный сайт продолжает работать на основном домене. Закрытый hostname получает отдельное правило Cloudflare Access.

### Cloudflare Access

Рекомендуемый вариант для одного владельца:

1. создать Self-hosted application для `constructor.shakurova-content.ru`;
2. использовать Cloudflare как identity provider;
3. ограничить политику участником нужного Cloudflare-аккаунта или конкретным email;
4. включить MFA на Cloudflare-аккаунте;
5. короткая длительность сессии, например 8–24 часа;
6. не создавать Bypass-политику для API;
7. проверить вход из режима инкогнито и с другого email.

One-time PIN на email допустим как резервный способ, но не должен быть единственной защитой при наличии Cloudflare account login с MFA.

## Защита origin и Worker

Cloudflare Access проверяет запрос до Worker, но Worker также должен валидировать JWT из заголовка:

`Cf-Access-Jwt-Assertion`

Причины:

- защита от ошибочной DNS- или route-конфигурации;
- защита API при прямом обращении;
- получение подтверждённого email пользователя;
- возможность записывать действия в `audit_log`.

### Переменные окружения

- `ACCESS_TEAM_DOMAIN` — домен вида `<team>.cloudflareaccess.com`;
- `ACCESS_AUD` — Audience tag Access application;
- `CONSTRUCTOR_ALLOWED_EMAIL` — дополнительная серверная allowlist-проверка;
- `DB` — D1 binding.

Секреты не хранятся в GitHub и не передаются в клиентский JavaScript.

## Серверная проверка каждого запроса

Алгоритм:

1. получить `Cf-Access-Jwt-Assertion`;
2. отклонить запрос без токена;
3. проверить подпись через публичные JWK Cloudflare Access;
4. проверить `aud`;
5. проверить срок действия;
6. извлечь email;
7. сравнить с `CONSTRUCTOR_ALLOWED_EMAIL`;
8. передать подтверждённый email в контекст запроса;
9. записывать изменяющие операции в `audit_log`.

Нельзя доверять email, присланному из формы или localStorage.

## Маршруты

Закрываются все маршруты hostname, включая:

- `/`;
- `/clients/*`;
- `/diagnostics/*`;
- `/knowledge/*`;
- `/pricing/*`;
- `/proposals/*`;
- `/api/*`;
- `/imports/*`;
- статические файлы с потенциально чувствительными экспортами.

## D1

В `wrangler.jsonc` позже добавляется реальный binding:

```jsonc
{
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "jamila-constructor",
      "database_id": "<CLOUDFLARE_D1_DATABASE_ID>",
      "migrations_dir": "migrations"
    }
  ]
}
```

`database_id` добавляется только после создания D1-базы в Cloudflare и не выдумывается заранее.

## Разделение публичного и приватного интерфейса

Даже при одном репозитории:

- публичные страницы не импортируют приватные данные;
- приватные запросы выполняются только на сервере;
- D1 не вызывается из браузера напрямую;
- закрытый layout не попадает в публичное меню;
- приватные страницы получают `noindex, nofollow`;
- ответы с данными используют `Cache-Control: no-store`;
- экспорт создаётся по запросу и не сохраняется в `/public`.

## Защита данных клиентов

### Не хранить без необходимости

- пароли;
- платёжные реквизиты карт;
- медицинские документы;
- детальные данные детей;
- полные документы личности;
- секреты сторонних сервисов.

### Чувствительные поля

Контактные данные, приватные переписки и внутренние заметки:

- показываются только в кабинете;
- не входят в экспорт базы знаний по умолчанию;
- не отправляются в AI без отдельного действия;
- удаляются или обезличиваются перед тестовыми импортами.

## Резервные копии

Минимальная политика:

- ручной JSON/CSV-экспорт перед крупным импортом;
- отдельная запись `import_batches`;
- отсутствие физических удалений использованных knowledge items;
- архивирование вместо удаления;
- журнал изменений для клиентских данных, тарифов и утверждённых ответов.
