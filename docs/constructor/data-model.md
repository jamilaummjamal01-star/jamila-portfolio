# Модель данных конструктора

## Принцип

Данные делятся на пять контуров:

1. справочники;
2. атомарная база знаний;
3. работа с клиентами;
4. расчёты и КП;
5. импорт, аудит и контроль качества.

## 1. Справочники

### `niches`

22 основные ниши.

Ключевые поля:

- `id`;
- `slug`;
- `name`;
- `description`;
- `priority` — A, B или C;
- `is_active`.

### `subniches`

Подниши и специализации внутри основной ниши.

Примеры:

- собственный бренд косметики;
- официальный дистрибьютор;
- продавец маркетплейса;
- частный специалист;
- образовательная организация;
- B2B-поставщик.

### `stages`

Этапы клиентского пути и переговоров.

Базовый набор:

1. предварительный аудит;
2. первое сообщение;
3. ответ на интерес;
4. экспресс-диагностика;
5. полная диагностика;
6. уточнение перед КП;
7. отправка КП;
8. обсуждение стоимости;
9. возражения;
10. согласование старта;
11. проект в работе;
12. сдача;
13. повторная продажа;
14. отказ.

### `tags`

Свободные тематические метки:

- упаковка;
- точность товара;
- права;
- сроки;
- бюджет;
- конфиденциальность;
- AI;
- реклама;
- маркетплейс;
- исламская этика.

## 2. Атомарная база знаний

### `knowledge_items`

Главная таблица конструктора.

Каждая запись содержит только один самостоятельный смысл.

#### Типы записи

- `question_to_client` — вопрос клиенту;
- `question_from_client` — вероятный вопрос клиента;
- `answer` — самостоятельный ответ;
- `objection` — возражение;
- `objection_response` — ответ на возражение;
- `clarifying_question` — уточнение;
- `first_message` — первое сообщение;
- `follow_up` — повторное сообщение;
- `diagnostic_hint` — подсказка диагностики;
- `audit_check` — что проверить до контакта;
- `red_flag` — риск;
- `ethical_rule` — этическое ограничение;
- `proposal_block` — блок коммерческого предложения;
- `package` — пакет услуг;
- `next_action` — рекомендуемое действие;
- `refusal_reason` — основание для отказа.

#### Содержательные поля

- `title` — внутреннее название;
- `prompt_text` — формулировка вопроса или сообщения;
- `short_text` — короткий вариант;
- `full_text` — подробный вариант;
- `soft_text` — мягкая версия;
- `firm_text` — твёрдая версия;
- `clarification_text` — следующий уточняющий вопрос;
- `next_action_text` — что сделать после ответа;
- `avoid_text` — чего не говорить;
- `diagnostic_value` — зачем эта запись нужна;
- `red_flag_text` — какой риск выявляется.

#### Управляющие поля

- `channel` — любой, Instagram, Telegram, WhatsApp, email, созвон;
- `tone` — нейтральный, тёплый, деловой, короткий, твёрдый;
- `required_level` — обязательный, рекомендуемый, дополнительный;
- `risk_level` — обычный, повышенный, высокий, отказ;
- `status` — черновик, на проверке, утверждено, архив;
- `conditions_json` — условия показа;
- `source_kind` — Notion, ручное добавление, реальный диалог, импорт;
- `source_url`;
- `version`;
- `reviewed_at`.

### Many-to-many связи

- `knowledge_item_niches`;
- `knowledge_item_subniches`;
- `knowledge_item_stages`;
- `knowledge_item_tags`.

Это позволяет не дублировать универсальные вопросы в каждой нише.

## 3. Клиенты и диагностика

### `clients`

Ключевые поля:

- название;
- ссылка;
- основной контакт;
- канал;
- город и география;
- бизнес-модель;
- продукт;
- аудитория;
- коммерческая задача;
- статус CRM;
- приоритет;
- бюджетный ориентир;
- следующий шаг;
- дата следующего контакта;
- этический статус;
- служебные заметки.

### `client_niches`

Связывает клиента с основной и дополнительными нишами.

### `diagnostic_sessions`

Отдельная сессия разговора или подготовки.

Поля:

- клиент;
- формат;
- статус;
- дата;
- канал;
- цель;
- главный диагноз;
- рекомендуемый пакет;
- следующий шаг;
- этическое решение.

### `diagnostic_session_items`

Фиксирует, какие вопросы были выбраны и что ответил клиент.

Поля:

- сессия;
- элемент базы знаний;
- порядок;
- был ли задан;
- ответ клиента;
- внутренняя заметка;
- выявлен ли риск;
- добавлено в итог.

### `favorites`

Избранные элементы базы знаний для быстрого доступа.

- состав;

- стоимость;

## 5. Импорт и контроль качества

### `import_batches`

Каждая загрузка из Notion или файла оформляется отдельной партией.

Поля:

- источник;
- дата;
- количество строк;
- импортировано;
- пропущено;
- ошибки;
- статус.

### `audit_log`

Журнал внутренних изменений:

- действие;
- сущность;
- ID сущности;
- email пользователя из Cloudflare Access;
- старое и новое значение;
- дата.

## Правила целостности

1. Утверждённая запись обязана иметь хотя бы одну нишу или быть универсальной.
2. Вопрос клиента должен иметь хотя бы короткий ответ либо связь с ответом.
3. Высокорисковая запись обязана содержать объяснение риска.
4. Запись для КП обязана иметь клиентскую формулировку без внутренних комментариев.
5. Архивные записи не участвуют в подборе.
6. Дубли определяются по нормализованному тексту, типу и контексту.
7. Удаление записи заменяется архивированием, если она уже использовалась в сессиях.
8. Источник и дата проверки сохраняются для каждой импортированной записи.

## Условия показа

`conditions_json` хранит дополнительные правила, которые нельзя выразить простым фильтром.

Пример:

```json
{
  "show_when": {
    "business_model": ["manufacturer", "own_brand"],
    "uses_paid_ads": true,
    "has_product_label": true
  },
  "hide_when": {
    "project_type": ["internal_only"]
  }
}
```

В MVP условия обрабатываются ограниченным безопасным набором ключей, а не произвольным кодом.
